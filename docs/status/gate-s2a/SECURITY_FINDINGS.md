This file records what was checked, what was found and what enforces each rule.

**Scope.** This is a prototype: the rules live in the typed mock server (`packages/fixtures/src/hr/`), and the backend must reproduce them at Gate H.

## 3. Residual risks (prototype)

- **The server is a mock.** Everything is enforced in an in-browser mock server; a real backend must re-implement each rule server-side (Gate H).
- **The demo can withdraw HR, and narrow a scope.** Both overrides live in `demo-licence.ts` and are read from sessionStorage:
  - the withdrawal can only remove grants, never add them;
  - the site-scope hook (Issue #14, for the browser tests and evidence) applies only to an organisation-wide scope and replaces it with named sites, so it can only narrow.

  Both are unit-tested (`demo-licence.test.ts`), and neither exists outside the prototype.
- **No routing for shared employees (Issue #14).** A single-site principal is refused any change to a multi-site employee's shared record, and nothing routes the request to someone responsible for every site. That is the fail-closed answer; a routing or approval contract needs its own design.
- **Seeing is still allowed through one site.** A main-site manager still reads a shared employee's record, including their personal details with `hr.manage` (Issue #12's read rule, unchanged). The record is read only for them.
- **"Own record" depends on the employee–user link.** It relies on the employee record carrying the user's principal id. Every Al-Noor staff user is linked in the demo. A real system must require the link for any employee who is also a user, or the check cannot see that it is their own record.
- **Free text is shown as text.** This covers reasons, notes and posts; React escapes it, and nothing is rendered as rich text or links.
- **Identity numbers** are validated for format and uniqueness only, not against NADRA.
- **Consent for the residents' view** is recorded by the office (who and when). There is no staff-side confirmation in S.2a (no staff self-service).
- **Settlement (S.2b).** Verified staff payments need a staff-advance voucher subject in S.1, naming the advance and the employee, and an approved category. They also need the reversal rule (a later reversal undoes the link). None of this exists yet, so linking is disabled rather than approximated.
- **Multi-site in the demo.** The demo has one site. Multi-site isolation is proven at the API with a fictional multi-site organisation; the screens use the same server answers. Since Issue #14, the browser tests also add a shared guard and a second site in the tab, to show the read-only Employee 360.
- **Transfers.** There is no transfer screen: dated site allocations are the record, and the tests edit them as a transfer would. A real transfer workflow must keep allocations consistent with the employing entity (an inconsistent record is visible to nobody).

## 4. Other findings (not security)

- **Times in Urdu were reordered.** The organisation's times carry Latin AM/PM in Urdu too, and the shared `DateTime` component does not isolate its text. Inside an Urdu line the bidi algorithm reordered "7:00 AM – 3:00 PM" into "AM – 3:00 PM 7:00". Found in the S.2a evidence review.
  - S.2a isolates each of its own times (`Time`, `ShiftTime`, `timeRangeText` in `hkit.tsx`; the residents' staff tab).
  - Other gates' screens that put a time inside an Urdu sentence may show the same. Isolating `DateTime` itself (`<bdi>` or `dir="auto"`) would fix them all, but it changes every gate's rendering. Owner ruling O10: a separate, independently tested change, not part of this closure.
- **Office dashboard wording (Issue #12).** For shifts with no minimum, the "Running now" card said "n on duty" while counting people not yet checked in. It now says "n scheduled".
- **Tabs and select values at 320 px with 200 % text.** Shared tab rows scrolled their tabs out of sight, and long select values ran past the field. Both were fixed in the shared components ([report §5](GATE_S2A_REPORT.md#5-design-and-accessibility)).
